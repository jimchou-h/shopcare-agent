## Context

访客查单已经提供同源页面、演示会话 Cookie、订单归属检查和持久化数据库。当前示例订单有签收状态与创建时间，换货资格还需要专门的签收时间。FAQ 已提供期限、商品条件和运费条款，可以复用原始条目作出处。

## Goals / Non-Goals

**Goals**

- 在默认 Docker 部署的对话页中用一笔自己的示例订单完成「我想换货 → 补充信息 → 核对摘要 → 确认 → 查看申请编号」。
- 让顾客看到明确的拒绝原因、安全重试或已有申请结果。

**Non-Goals**

- 本轮的业务终态为「已提交」。审批、撤销已提交申请、库存、物流与转人工由后续需求定义。

## Decisions

### 对话入口和状态机

- React 将当前页面的顾客问题、助手回复、订单卡片和确认卡片呈现在同一个消息列表中。顾客可输入「我想换货」，也可点击订单消息里的「申请换货」。助手核对归属并展示当前示例订单。会话缺失时在消息中引导领取。
- 服务端用 TypeScript 的显式状态机推进「等待原因 → 等待商品申报 → 等待确认 → 已提交」。原因可选择「质量问题」或「其他原因」。申报消息列出商品完好、配件与原包装齐全、未影响二次销售，以及适用时的赠品条件，顾客据此明确回答。页面可提供选项按钮，通过同一个对话入口提交对应的受控回答。
- `POST /api/chat` 沿用 `{ question }` 请求，新增结构化换货回复。状态机只接受当前步骤能够解析的回答，其他内容获得澄清提示或按现有 FAQ 流程处理。明确的 FAQ 提问保留换货进度。进入换货时清除查单的待补单号状态；换货进行中若请求启动新的查单补问，提示先完成或取消当前换货。
- 每个访客只保留一个进行中的换货流程，SQLite 按会话保存当前步骤及必要字段。明确取消会结束未提交的流程并使对应摘要失效。「继续换货」可重新取得当前提示或有效摘要，换货进度与最终申请随有效会话恢复。页面会话内展示多轮消息，恢复时可从当前办理步骤继续。
- 本轮采用 TypeScript 状态机与现有 SQLite，显式记录可接收的事件、转移和副作用。LangGraph 的检查点、中断恢复与图编排能力适合后续多个流程共享编排时重新评估。资格校验和写入留在业务用例中，未来可从图节点调用。

### 聊天页面与组件库

- 页面固定为单列聊天布局：顶部展示会话与示例订单操作，中间是可滚动消息流，底部固定输入区。用户消息右对齐，助手消息左对齐；问答、查单、换货步骤、摘要与回执都作为消息追加，刷新后的会话与办理进度仍由服务端恢复。
- 引入 antd 作为基础组件库，使用 `ConfigProvider`、`Input`、`Button`、`Card`、`Descriptions`、`Alert`、`Space`、`Typography`、`Tag`、`Empty` 与 `Spin` 替换手写表单和卡片样式。`styles.css` 只保留全局重置、聊天骨架和消息气泡布局，减少自维护样式。
- 商品现状不使用关键词推断：换货步骤返回「齐全」「不齐全」两个明确选项，服务端只接受这些明确值（以及「完整 / 不完整 / 缺件」等价选项），其余自由文本返回同一步骤并提示重新选择；`都齐全`、`有缺失` 等旧别名不再识别。申报步骤默认继续二选一，只有内容明确命中政策主题（期限、运费、几天、什么时候、政策、资格等）时才交给 FAQ，不再枚举「齐全吗」「是否齐全」等疑问句式。回答先按标点切分成段再匹配：保留问号；整句只允许「确认词段 + 唯一一个明确选项段」，出现任何其它无法识别的分段都回到二选一提示，不静默忽略，也不靠风险词枚举。
- 订单查询消息不再渲染换货表单，只保留订单信息、已提交回执和「回复『我想换货』继续办理」提示；换货统一走对话状态机，预览与确认接口保持不变。
- CSP 使用按请求生成的 nonce：`onRequest` 生成 nonce 并写入响应头，页面路由把同一值注入 `meta[name="csp-nonce"]`，antd 通过 `ConfigProvider.csp.nonce` 让运行时 `<style>` 携带该 nonce。`script-src` 保持 `'self'`，只对样式元素使用 nonce、对样式属性放开内联，避免为了样式而放宽脚本策略。
- 样式回归测试覆盖消息顺序、底部固定输入区、antd 控件渲染、订单消息不含换货表单，以及既有换货消息流程；CSP 测试覆盖 nonce 唯一性、页面 meta 注入与脚本策略约束。

### 资格和提交边界

- 对话收齐信息后复用换货预览用例，沿用 `POST /api/exchange/preview` 的资格校验与摘要契约。聊天里的确认按钮调用 `POST /api/exchange/confirm`。相关请求复用现有访客身份、订单归属检查、同源校验和公开入口限流。查单与换货数据均留在本地业务链路。
- 资格按签收状态、签收日期和申报条件判断。期限按演示时区 `Asia/Shanghai` 的自然日计算，签收日为第 1 天，第 7 天全天可提交，第 8 天零时起逾期。服务端判断用当前时钟。摘要根据原因给出政策运费说明，引用 FAQ 中的期限、商品条件和费用条款。
- SQLite 增量迁移新增签收时间。旧合成种子在领取时就创建「已签收」订单，因此这批演示订单以创建时间补齐模拟签收时刻，保留原单号及有效会话。后续种子明确写入签收时间。测试用可控时钟验证日期边界和确认前资格变化。

### 明确确认与幂等

- 预览仅保存一份待确认摘要，产生一个不透明的确认 ID，有效期为 10 分钟。摘要绑定服务端识别的访客、订单、原因和申报。重新预览会替换旧摘要，顾客修改原因或申报后须重新生成摘要。
- 顾客点击当前摘要上的「确认提交」，请求只携带确认 ID。对话文本「确认」只会提示顾客查看并点击当前摘要。服务端在同一 SQLite 事务中检查归属、摘要状态和当前资格，再写入含确认 ID 的申请记录。确认 ID 作为幂等键。同一确认已成功提交时，事务直接返回原申请。过期、已取消或被替换且尚未提交的摘要要求重新预览。
- 申请表对订单与确认 ID 分别设唯一约束。即使点击两次、并发请求或服务端写入后响应丢失，一笔示例订单也只会有一笔申请。失败可重试。同一会话在查询自己的订单时也可看到原申请编号和状态。

### 数据与模块

- 在 `src/server/exchange/` 按对话状态机、资格和应用用例组织换货行为。现有查单、会话、FAQ 与模型仍由各自模块处理。SQLite 迁移沿用 `src/server/db/`，写事务包含资格复核和幂等记录。网页通过 `src/shared/` 中的契约消费结果。
- 申请和待确认摘要归属演示订单。延续现有演示数据寿命，订单随过期会话清理时清理其关联记录。查询与重试都先校验会话和归属。
- 自动化覆盖 Fastify 实际入口、React 行为和 SQLite 并发与持久化。Compose 冒烟验证无 Key、保留数据卷重建和申请编号恢复。

## Risks / Trade-offs

- 演示订单依据用户申报判断商品情况。界面使用「已提交」表明系统已接收申请。
- 预览与确认之间可能跨过期限。确认时复核资格，引导已经逾期的顾客查看原因。
- 提交后断网可能导致浏览器看不到成功结果。保留同一确认 ID 重试，刷新后也可从原订单恢复回执。

## Migration Plan

沿用查单的数据卷和版本化迁移。升级时补齐现有演示订单签收时间并创建换货相关表；验证旧订单仍可查、有效会话仍可进入换货流程。回滚镜像时保留原数据卷。
