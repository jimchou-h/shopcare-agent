## ADDED Requirements

### Requirement: 访客文本在业务分发前经过校验

系统 SHALL 在业务分发和模型请求之前执行文本长度、提示注入和话题范围校验。被拦截的请求 MUST 得到可理解的固定提示，且 MUST 保持订单与办理状态原样。

#### Scenario: 违规输入不会推进办理

- **WHEN** 正在补充换货信息的访客发送命中护栏的明确注入请求或明显超出售后范围的文本
- **THEN** API 返回 HTTP 200 和 `blocked`，原因区分 `prompt_injection` 与 `off_topic`，对话显示固定提示
- **AND** 服务端没有推进或清空当前步骤，也没有发起模型请求
- **AND** 访客随后可继续原步骤

#### Scenario: 正常业务消息继续处理

- **WHEN** 顾客提交正常的政策问法、查单、明确换货操作或当前步骤的结构化选项
- **THEN** 页面按既有规则显示回答、澄清或业务结果
- **AND** 只因语料缺少依据而无法回答的问题继续走已有澄清路径

#### Scenario: 询问售后页面提示时仍可办理

- **WHEN** 顾客用「系统提示」描述售后界面上的问题或请求补充办理信息
- **THEN** 系统按既有业务或澄清路径处理，不因单独命中该词而拦截

#### Scenario: 超长请求在业务处理前被拒绝

- **WHEN** 顾客提交超过文本长度契约或 HTTP 请求体限制的请求
- **THEN** 服务端予以拒绝，且没有新增业务记录或模型请求

### Requirement: 模型请求与回复中的个人信息得到脱敏

系统 SHALL 在构造上游模型请求和返回模型生成正文的位置，遮盖识别到的手机号、身份证号和邮箱。拦截或失败响应 MUST 排除原始上游内容与原始个人信息。

#### Scenario: 模型收到脱敏后的问题

- **WHEN** 启用模型的实例收到含支持格式个人信息的正常政策问题，且需要模型生成
- **THEN** 上游收到遮盖该信息的问题，合法的政策证据仍可用于生成

#### Scenario: 回复脱敏并保留出处

- **WHEN** 模型替身返回通过政策证据校验的结构化结果，正文含支持格式的手机号、身份证号或邮箱
- **THEN** 页面展示遮盖后的正文及同一条政策出处，响应中没有该原始个人信息

#### Scenario: 保留正常业务数字

- **WHEN** 待发送的模型问题或待展示的模型正文同时包含支持格式的个人信息与普通业务数字
- **THEN** 对应文本保留普通业务数字，识别到的个人信息被遮盖

#### Scenario: 模型失败时只展示受控结果

- **WHEN** 上游错误或生成结果校验失败，原始内容中包含个人信息
- **THEN** 页面展示有证据的降级答复或固定失败提示，响应不包含原始个人信息
