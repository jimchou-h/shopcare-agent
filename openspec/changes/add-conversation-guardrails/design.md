## Context

现有聊天路由先做来源、频率和请求结构校验，再按换货、查单、政策问答分发。DeepSeek 生成结果已做结构、引用和政策事实校验。新增护栏覆盖访客文本和模型回复各自的边界。

## Goals / Non-Goals

**Goals**

- 顾客发出明显越界或试图改变系统指令的请求时，页面给出可继续咨询的提示。
- 进入模型的用户问题与展示的模型正文采用同一套个人信息脱敏规则。
- 用正常和异常样本、可控模型替身和真实聊天入口验证边界。

## Decisions

### 输入校验

- 复用 HTTP 请求体与文本长度限制。在请求结构通过后、读取或推进业务流程前校验 `question`。输入护栏覆盖明确的提示注入意图和明显与售后无关的请求。无法确定话题时由现有的证据不足、澄清或补问路径处理。正常售后问题、换货原因、申报和取消语句进入业务分发。
- 结构化按钮动作走原有 schema、会话归属和交互标识校验。文本被拦截时不调用业务用例或模型，不清空或推进已有步骤。API 返回稳定的拦截类型和固定提示，React 将其作为助手消息追加。
- 护栏拦截属于一次已处理的对话。沿同源 `POST /api/chat` 返回 HTTP 200 和 `{ status: "blocked", reason, message }`。原因使用 `prompt_injection` 或 `off_topic`，页面显示固定引导「我可以帮你查询订单、办理换货或解答售后政策。」请求结构、长度和频率异常沿用现有错误契约。

### 个人信息脱敏

- 在 `src/server/guardrails/` 集中实现手机号、身份证号与邮箱脱敏。访客文本可在本地用于判断意图与检索，构造模型请求时使用处理后的问题。订单和确认数据沿用已有本地处理边界。
- 对生成结果先校验结构、候选引用和政策事实，再遮盖将返回页面的模型正文。保留可信语料的条目标识和政策出处字段。异常响应走现有降级路径，拦截提示、错误与诊断只使用固定文案或类型，避免记录含个人信息的原始输入和上游正文。

### 验收样本

- 输入样本至少记录稳定 ID、原文、场景上下文和期望结果。上下文覆盖普通问答和正在办理换货。样本各自标明放行、拦截原因或现有澄清路径。「换货规则是什么？」和「退货邮费谁承担？」分别用于验收正常政策问题和证据不足时的既有行为。用提及「系统提示」的正常售后问题检查是否存在单一关键词误拦。
- 脱敏样本分别标明个人信息类型、出现位置、原文和期望遮盖结果。覆盖模型请求、模型回复、一段文本含多项信息，以及普通订单号和政策时限。测试数据使用合成内容。模型替身捕获实际请求并返回固定文本，API 回归再检查用户收到的正文和出处。
- 少量代表场景通过真实 HTTP 入口验证状态和模型调用次数。同类措辞放进可复用的标注样本。整体评测运行器和多路召回由后续 Change 定义。

## Risks / Trade-offs

- 文本规则覆盖已定义的输入模式与个人信息格式。验收同时关注应拦截请求和容易被误拦的正常业务问法。
- 参考项目的输入检查和输出脱敏是实现基准。ShopCare 同时在构造模型请求时脱敏个人信息，验收时检查模型替身收到的实际内容。
