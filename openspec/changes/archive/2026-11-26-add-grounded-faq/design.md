## Context

仓库已完成 OpenSpec 和 GitHub Issues 的配置。第一条业务路径是可从浏览器验证的中文售后问答。后续真实模型和订单能力沿既定 Change 顺序加入。

## Goals / Non-Goals

**Goals**

- 使用小型、可公开发布的合成 FAQ 建立引用正确与证据不足两种可重复的反馈。
- 使用一个生产容器同源提供页面和 API，方便从干净环境复现验收。

**Non-Goals**

- DeepSeek 接入、业务状态持久化、换货写入、模拟坐席和公网发布进入后续 Change。

## Decisions

1. **同源 HTTP。** React/Vite 页面向 Fastify 的 `POST /api/chat` 提交一轮问题。首条路径使用 JSON，一次返回结论和来源，便于直接验证证据是否与答案对应。
2. **确定性检索与回答。** 版本化的 FAQ 条目包含稳定 ID、标题、可检索问法和政策正文。参考工程作为语料结构和用例设计的参考。对输入做基本规范化，按可解释的中文关键词匹配选择条目。遇到无匹配或无法唯一确定的匹配时提示补充。命中的文本和出处来自同一条语料。
3. **在入口建验证。** API 验证输入并返回稳定的业务结果。页面将回答、引用和证据不足的提示作为可读文本渲染。用固定语料测试两种等价问法、无证据、空输入与服务异常的呈现。
4. **单容器部署。** Docker Compose 构建应用，Fastify 同源提供产物。`GET /healthz` 在服务可读取有效 FAQ 后报告就绪。从干净环境验收时仅使用仓库内配置与样例。

## Risks / Trade-offs

- 关键词方案遇到未覆盖的同义表达时会漏召回。证据不足时引导用户补充，并用固定场景保存首版基线。
- 浏览器生产构建和本地开发的资源路径可能不同。以容器提供的页面、API 和就绪状态做一轮独立冒烟。
