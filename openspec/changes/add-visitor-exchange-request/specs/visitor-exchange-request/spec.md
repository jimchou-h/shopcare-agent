## ADDED Requirements

### Requirement: 顾客核对自己订单的换货资格

系统 SHALL 在默认无模型 Key 的演示部署中，在与政策问答和查单相同的对话内为顾客发起换货，并逐步询问缺少的信息。资格 MUST 由服务端根据订单归属、签收状态、签收日起 7 天以内和顾客申报的商品条件判断。换货业务数据 MUST 在服务端本地办理。有效预览 MUST 展示待确认的申请内容和对应政策出处。

#### Scenario: 符合资格时展示确认摘要

- **WHEN** 顾客输入「我想换货」，依次在对话中选择换货原因和商品现状「齐全」
- **THEN** 助手先后显示当前步骤的问题，信息齐备且订单符合资格时在消息中展示订单、原因、适用运费、政策出处和「确认提交」按钮
- **AND** 质量问题显示商家承担往返运费，其他原因显示顾客承担寄回运费
- **AND** 此时没有已提交的换货申请，模型不参与换货

#### Scenario: 办理途中询问售后政策

- **WHEN** 助手正在等待商品申报，顾客插问「换货期限是多久？」
- **THEN** 对话按现有问答规则提供政策结论和出处
- **AND** 下一轮补充商品申报时，办理过程沿用原订单和已收集的原因

#### Scenario: 一次只推进一项补问流程

- **WHEN** 访客在待补查单单号时明确发起换货，或在换货过程中发起缺少单号的查单请求
- **THEN** 发起换货时结束查单补问；换货过程中出现新的查单补问请求时提示先完成或取消换货

#### Scenario: 第七天可以申请，第八天截止

- **WHEN** 已签收的订单满足商品条件，顾客分别在演示时区的签收第 7 天和第 8 天请求预览
- **THEN** 第 7 天可进入确认，第 8 天显示逾期原因及对应政策出处

#### Scenario: 未签收或商品条件不满足时说明原因

- **WHEN** 顾客的订单尚未签收，或顾客申报商品不满足换货条件
- **THEN** 页面显示相应原因及政策出处，无法确认提交

#### Scenario: 商品现状使用明确选择

- **WHEN** 顾客完成换货原因后，助手询问商品现状
- **THEN** 助手在消息中展示「齐全」和「不齐全」两个选项
- **WHEN** 顾客选择「不齐全」
- **THEN** 系统按商品条件不满足说明原因与政策出处
- **AND** 不生成可提交的确认摘要，也不写入申请

#### Scenario: 自由文本无法判断时不猜测

- **WHEN** 顾客回复无法归类的自由描述，例如「商品不完好」
- **THEN** 助手不推断商品是否齐全，重新提示选择「齐全」或「不齐全」
- **AND** 不生成摘要，当前步骤与已选原因保持不变

#### Scenario: 申报步骤默认继续二选一

- **WHEN** 顾客在申报步骤回复无法识别为明确选项的内容，例如「齐全？」「这个算齐全吗」「齐全了吗」
- **THEN** 助手重新提示选择「齐全」或「不齐全」，不生成摘要，已选原因和当前步骤保持不变
- **AND** 只有在明确询问政策主题（期限、运费、几天、什么时候、政策等）时才转给政策问答
- **AND** 只有「齐全 / 不齐全」及其明确等价选项（完整 / 不完整 / 缺件）会推进资格判断

#### Scenario: 归属验证失败时不给出订单信息

- **WHEN** 访客未建立有效会话，或者请求预览、确认或读取另一访客的换货申请
- **THEN** 页面引导领取自己的示例订单或提示无法办理，响应不包含其他访客的订单、摘要和申请详情

### Requirement: 顾客明确确认后提交一次申请

系统 SHALL 仅在顾客通过当前对话摘要明确确认后创建换货申请。确认请求 MUST 来自页面同源并关联有效访客会话。服务端 MUST 验证摘要归属和当前资格，并保证同一订单至多有一笔申请。同一确认的成功重试 MUST 返回原结果。

#### Scenario: 确认后获得申请编号

- **WHEN** 顾客点击有效摘要上的「确认提交」，订单仍符合换货资格
- **THEN** 页面显示申请编号和「已提交」状态

#### Scenario: 聊天文本确认不产生申请

- **WHEN** 等待确认时顾客在输入框发出「确认」
- **THEN** 助手指向本次摘要的「确认提交」按钮，数据库没有申请写入

#### Scenario: 重复提交同一份确认

- **WHEN** 同一有效会话重复或并发提交同一个确认 ID
- **THEN** 成功响应返回同一申请编号，数据库只有一笔申请

#### Scenario: 摘要失效或资格变化时需要重新核对

- **WHEN** 顾客提交尚未使用但已过期、被替换或取消的摘要，或订单已越过换货期限
- **THEN** 系统说明失效原因并引导重新核对，数据库没有新增申请

#### Scenario: 重新发起后旧确认失效

- **WHEN** 顾客已生成摘要但尚未提交，随后重新发起换货并选择新的原因
- **THEN** 提交旧摘要返回失效结果，数据库不新增申请
- **AND** 只有最新摘要可以提交，并采用最新选择的原因与运费条件

#### Scenario: 跨来源请求不会提交申请

- **WHEN** 页面以外的来源携带有效会话与确认 ID 发起确认
- **THEN** 服务端拒绝请求，申请和待确认摘要状态保持原样

### Requirement: 顾客可安全恢复并查看已提交申请

系统 SHALL 在 SQLite 中持久化当前办理步骤、申请和幂等结果。顾客 MUST 能在有效会话内恢复办理或重新查看自己的申请。确认请求中断时，页面 SHALL 支持复用原确认重试。

#### Scenario: 刷新后继续当前办理步骤

- **WHEN** 顾客已选择换货原因，刷新页面后在原有效会话中发出「继续换货」
- **THEN** 助手恢复等待商品申报的提示，随后生成的摘要保留已选择的原因

#### Scenario: 取消尚未提交的换货

- **WHEN** 顾客看到待确认摘要后说「取消换货」
- **THEN** 助手结束本次办理并显示取消结果
- **AND** 再提交原摘要无法创建申请

#### Scenario: 询问取消方法不会结束办理

- **WHEN** 办理过程中顾客用疑问说法询问取消方式，例如「如何取消换货？」「怎么取消换货」「取消换货的方法」
- **THEN** 对话按政策问答回应，保留当前步骤、订单和已选原因
- **AND** 下一轮补充商品申报仍可生成摘要

#### Scenario: 已写入但响应中断

- **WHEN** 服务端已创建申请，顾客未收到响应并重试原确认
- **THEN** 页面显示原申请编号与状态，数据库仍只有一笔申请

#### Scenario: 页面刷新和容器重建后仍可查看

- **WHEN** 顾客已提交换货申请，刷新页面或使用同一数据卷重建容器后再次查询自己的订单
- **THEN** 页面展示同一申请编号和「已提交」状态
- **AND** 独立浏览器会话无法查看该订单的申请

### Requirement: 页面以对话形式承载售后办理

系统 SHALL 把售后问答、查单和换货办理呈现在同一条对话流中。用户消息与助手消息按时间顺序追加，输入区 MUST 固定在页面底部，顾客发送后仍可继续输入。换货办理 MUST 在对话消息中完成，不再要求顾客填写订单卡片内的独立表单。页面 SHALL 使用 antd 组件库呈现输入、按钮、消息卡片、提示与订单信息，手写样式仅保留页面骨架和消息气泡布局。

#### Scenario: 消息按对话流追加且输入固定在底部

- **WHEN** 顾客连续提交售后问题或换货步骤
- **THEN** 用户消息和助手消息按提交顺序追加到同一消息列表
- **AND** 输入框与发送按钮固定在页面底部，滚动消息时保持可见
- **AND** 页面刷新后可以在同一会话继续发送消息

#### Scenario: 查单结果引导在对话内办理换货

- **WHEN** 顾客查询到自己的示例订单
- **THEN** 订单消息展示单号、商品、订单状态和已提交申请的编号（如有）
- **AND** 页面提示回复「我想换货」在对话里继续办理
- **AND** 页面不出现订单卡片内的换货原因、申报或预览表单

#### Scenario: 换货步骤与摘要作为助手消息呈现

- **WHEN** 顾客依次补充换货原因、商品申报并生成摘要
- **THEN** 当前步骤的提示、快捷选项、摘要、运费说明、政策出处和「确认提交」按钮都出现在对应的助手消息中
- **AND** 提交成功后申请编号与「已提交」以消息形式展示，原有问答和查单消息保持可见

#### Scenario: 组件库提供可访问的表单与操作

- **WHEN** 页面渲染输入框、发送按钮、换货选项和确认按钮
- **THEN** 这些控件由 antd 组件渲染，输入框具有可访问名称「你的问题」
- **AND** 顾客可以通过键盘输入并提交，控件的禁用与加载状态随请求变化

### Requirement: 页面安全策略允许组件库样式并保持脚本约束

系统 SHALL 为每个页面响应生成独立的 CSP nonce，并把同一值写入页面 meta 与 antd 运行时注入的样式。`script-src` MUST 保持仅允许同源脚本，MUST NOT 为脚本引入 `'unsafe-inline'` 或 `'unsafe-eval'`。仅样式属性可以放开内联，未知来源的脚本、对象、框架嵌入和外部连接继续被拒绝。

#### Scenario: antd 运行时样式在严格脚本策略下生效

- **WHEN** 顾客打开页面
- **THEN** 响应包含带 nonce 的样式元素规则，脚本仍只允许同源
- **AND** antd 注入的 `<style>` 携带与页面 meta 相同的 nonce，组件样式正常呈现
- **AND** 两次响应使用不同 nonce

#### Scenario: 未知来源脚本仍被拒绝

- **WHEN** 页面尝试加载非同源脚本或执行内联脚本
- **THEN** 安全策略阻止执行
- **AND** 策略中不存在用于脚本的 `'unsafe-inline'` 或 `'unsafe-eval'`
