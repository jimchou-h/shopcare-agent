## ADDED Requirements

### Requirement: 顾客核对自己订单的换货资格

系统 SHALL 在默认无模型 Key 的演示部署中，为顾客自己的订单提供换货预览。资格 MUST 由服务端根据订单归属、签收状态、签收日起 7 天以内和顾客申报的商品条件判断。换货业务数据 MUST 在服务端本地办理。有效预览 MUST 展示待确认的申请内容和对应政策出处。

#### Scenario: 符合资格时展示确认摘要

- **WHEN** 顾客为自己在期限内签收的订单选择换货原因，确认商品符合条件并请求预览
- **THEN** 页面展示订单、原因、适用的运费说明及政策出处，并可明确确认提交
- **AND** 质量问题显示商家承担往返运费，其他原因显示顾客承担寄回运费
- **AND** 此时没有已提交的换货申请，模型不参与换货

#### Scenario: 第七天可以申请，第八天截止

- **WHEN** 已签收的订单满足商品条件，顾客分别在演示时区的签收第 7 天和第 8 天请求预览
- **THEN** 第 7 天可进入确认，第 8 天显示逾期原因及对应政策出处

#### Scenario: 未签收或商品条件不满足时说明原因

- **WHEN** 顾客的订单尚未签收，或顾客申报商品不满足换货条件
- **THEN** 页面显示相应原因及政策出处，无法确认提交

#### Scenario: 归属验证失败时不给出订单信息

- **WHEN** 访客未建立有效会话，或者请求预览、确认或读取另一访客的换货申请
- **THEN** 页面引导领取自己的示例订单或提示无法办理，响应不包含其他访客的订单、摘要和申请详情

### Requirement: 顾客明确确认后提交一次申请

系统 SHALL 仅在顾客确认本次换货摘要后创建换货申请。确认请求 MUST 来自页面同源并关联有效访客会话。服务端 MUST 验证摘要归属和当前资格，并保证同一订单至多有一笔申请。同一确认的成功重试 MUST 返回原结果。

#### Scenario: 确认后获得申请编号

- **WHEN** 顾客点击有效摘要上的「确认提交」，订单仍符合换货资格
- **THEN** 页面显示申请编号和「已提交」状态

#### Scenario: 重复提交同一份确认

- **WHEN** 同一有效会话重复或并发提交同一个确认 ID
- **THEN** 成功响应返回同一申请编号，数据库只有一笔申请

#### Scenario: 摘要失效或资格变化时需要重新核对

- **WHEN** 顾客提交尚未使用但已过期或被替换的摘要，或订单已越过换货期限
- **THEN** 系统说明失效原因并引导重新核对，数据库没有新增申请

#### Scenario: 跨来源请求不会提交申请

- **WHEN** 页面以外的来源携带有效会话与确认 ID 发起确认
- **THEN** 服务端拒绝请求，申请和待确认摘要状态保持原样

### Requirement: 顾客可安全恢复并查看已提交申请

系统 SHALL 在 SQLite 中持久化申请和幂等结果。顾客 MUST 能在有效会话内重新查看自己的申请。确认请求中断时，页面 SHALL 支持复用原确认重试。

#### Scenario: 已写入但响应中断

- **WHEN** 服务端已创建申请，顾客未收到响应并重试原确认
- **THEN** 页面显示原申请编号与状态，数据库仍只有一笔申请

#### Scenario: 页面刷新和容器重建后仍可查看

- **WHEN** 顾客已提交换货申请，刷新页面或使用同一数据卷重建容器后再次查询自己的订单
- **THEN** 页面展示同一申请编号和「已提交」状态
- **AND** 独立浏览器会话无法查看该订单的申请
